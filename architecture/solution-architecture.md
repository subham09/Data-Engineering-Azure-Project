# Solution Architecture
## Retail Sales Analytics Platform on Microsoft Fabric

---

## Architecture Decision: Why Microsoft Fabric?

Microsoft Fabric provides a **unified SaaS analytics platform** that combines all layers of the data stack — ingestion, storage, transformation, modeling, and reporting — under a single governance umbrella (OneLake). This eliminates the need to manage separate services (Azure Data Factory, Azure Synapse, Azure Data Lake, Power BI Premium) and reduces integration complexity.

---

## Component Selection Rationale

### Storage: Lakehouse vs. Data Warehouse

| Consideration | Decision |
|---|---|
| Raw + semi-structured data ingestion | **Lakehouse** (schema-on-read, Delta Lake) |
| Dimensional model for BI | **Data Warehouse** (T-SQL, ACID transactions) |
| Large-scale Spark transformations | **Lakehouse notebooks** (PySpark) |
| Power BI reporting | **Both** via DirectLake (Lakehouse) or SQL endpoint (DW) |

The project uses **both** — Lakehouse for the transformation pipeline, DW for the curated star schema.

### Transformation: Notebooks vs. Dataflow Gen2 vs. T-SQL

| Data Volume | Complexity | Tool Selected | Reason |
|---|---|---|---|
| Large (>100MB) | Complex joins, dedup | **PySpark Notebook** | Distributed compute, full Python ecosystem |
| Small-medium | Simple type-cast, filter | **Dataflow Gen2** | Low-code, Power Query familiarity |
| DW → DW | SQL-native | **T-SQL Script** | Runs natively in Fabric DW engine |

### Real-Time: Eventstream + Eventhouse

Eventstream provides managed event routing without Kafka cluster management. Eventhouse (KQL) is optimized for high-throughput time-series data — significantly faster than running similar queries in Spark SQL for streaming use cases.

## Data Flow Detail

```
Phase 1: BATCH INGESTION (daily, 6 AM UTC)
─────────────────────────────────────────────────────────
CSV files uploaded to OneLake Files/raw/
        │
        ▼ (Data Pipeline: PL_Master_RetailSalesLoad)
        │
        ├─► Notebook 01: Bronze Ingestion
        │       • Read CSVs with explicit schema
        │       • Add audit columns (_source_file, _ingestion_ts)
        │       • Write as Delta to bronze.* tables
        │       • OPTIMIZE + ZORDER for query performance
        │
        ├─► Notebook 02: Silver Transformation
        │       • Type cast all string columns
        │       • Deduplicate via window function
        │       • Apply business rules + DQ flag columns
        │       • Delta MERGE for SCD Type 1 upserts
        │
        ├─► Notebook 03: Gold Aggregation
        │       • Build dimensional model (dims + facts)
        │       • Pre-aggregate daily/customer metrics
        │       • Partition fact tables by date
        │       • Z-order on key join columns
        │
        └─► DW Load
                • Cross-item query: Gold Lakehouse → Fabric DW
                • MERGE dimensions (SCD Type 1)
                • Incremental watermark-based fact load
                • Refresh mart views

Phase 2: REAL-TIME STREAMING (continuous)
─────────────────────────────────────────────────────────
Order events generated by application
        │
        ▼ (Eventstream: ES_OrderEvents)
        │
        └─► Eventhouse: RetailEventsDB
                • Table: OrderEvents (raw, 90-day retention)
                • Update Policy: enrich with hour/day metadata
                • Materialized View: OrderSummary24h
                  (auto-refreshed aggregation)
                • Real-time KQL queries for dashboards

Phase 3: SEMANTIC MODEL + REPORTING
─────────────────────────────────────────────────────────
Gold Lakehouse tables
        │
        ▼ (DirectLake connection — no data copy)
        │
        └─► Semantic Model: RetailSalesSemanticModel

                • DAX measures (revenue, AOV, conversion)

                │
                └─► Power BI Reports / Dashboards
```

## OneLake as Single Storage Layer

OneLake is the centralized storage for all Fabric items. Key properties:
- **Single copy of data** — Lakehouse, DW, and Semantic Model all read from the same OneLake files
- **Delta Lake format** — ACID transactions, time travel, schema evolution
- **Shortcuts** — virtual pointers to external ADLS/S3 without data duplication
- **Fabric-wide governance** — one set of access controls, one audit log

## Performance Design Decisions

| Decision | Rationale |
|---|---|
| Delta OPTIMIZE + ZORDER after each load | Compact small files from streaming writes; Z-order improves filter pushdown on join keys |
| Partition `fact_orders` by `order_date` | Partition pruning eliminates scanning years of history on date-range queries |
| Materialized views in Eventhouse | Pre-compute hourly aggregates once; serve many dashboard queries cheaply |
| `staging.watermark` table in DW | Simple, DW-native watermark tracking avoids external state management |
| Gold tables in DirectLake mode | Zero-copy reads from Delta files into Power BI — eliminates import refresh lag |

## Scalability Notes

| Scale Point | Current Setup | Path to Scale |
|---|---|---|
| Source data volume | Sample: ~10K customers, ~50K orders | Notebooks auto-scale with Fabric Spark capacity |
| Streaming throughput | Dev: simulated events | Production: connect Eventstream to Event Hubs / IoT Hub |
| Report users | Small team | Fabric capacity F4+ for more concurrent queries |
| Historical data | 2020–2026 | Extend date dimension; add more partitions |
